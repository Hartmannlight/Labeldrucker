# Refactoring baseline (2026-09-08)

This inventory is the AP-00 baseline for replacing PrinterFleet with direct
print-service integrations. It records behavior and ownership, not a promise
that every historical deployment file is still supported.

## Source state

- Root repository: branch `main`, commit `ce0f45f` before implementation work.
- ZebraTamer: branch `codex/print-agent-protocol`, commit `931d93a`.
- PrintHub: branch `codex/printer-fleet-boundary`, commit `1f1faa4`.
- The root worktree already contained unrelated modified and deleted files.
  They must be preserved and are not part of this baseline.

## Existing runtime path

```text
Studio / API / IPP
        -> PrintHub prepares ZPL or a neutral raster page
        -> PrinterFleet queues, encodes and routes the payload
        -> RAW TCP printer or ZebraTamer
        -> physical/virtual Zebra
```

- PrintHub stores logical print jobs in its data directory, but depends on the
  Fleet HTTP adapter for printer lookup, submission and downstream status.
- Fleet owns the direct TCP transport, raster-to-ZPL conversion, a smaller
  Zebra status implementation, maintenance commands, registry and global
  delivery queue.
- ZebraTamer already owns durable local jobs, per-printer FIFO workers,
  idempotency, conservative restart recovery, Zebra status/configuration,
  media accounting and USB/character-device transports.
- The root IPP gateway uses CUPS `ippeveprinter` and sends accepted documents to
  PrintHub. PrintHub performs PDF/image/PWG/URF conversion. The gateway is a
  separate image, although its source currently lives in the root repository.

## Data that must survive the cutover

| Source | Required data |
| --- | --- |
| Fleet registry | Public printer IDs/names, direct TCP endpoints, agent identity/local ID, enabled state and operator-confirmed profiles |
| Fleet deliveries | Terminal history; active or unknown outcomes must be reported and must never be submitted as new device jobs automatically |
| PrintHub data | Templates, drafts, counters, logical jobs, source documents, immutable prepared artifacts and downstream job references |
| ZebraTamer data | Stable service identity, jobs/idempotency records, queues, observations, media state/history and configuration attempts |
| IPP data | Stable queue IDs, TLS material and spool entries that have not been durably handed to PrintHub |

Secrets are deliberately excluded from inventory output. Migration tools may
read them from their original protected locations but must not print them.

## Behavior replacement map

| Fleet behavior being removed | Replacement owner |
| --- | --- |
| Direct RAW TCP/9100 | ZebraTamer TCP transport |
| Raster page to Zebra graphics | ZebraTamer ZPL driver |
| Zebra status and maintenance | ZebraTamer existing device worker plus allowlisted actions |
| Physical FIFO and restart recovery | ZebraTamer durable per-printer queue |
| Printer pause/resume | ZebraTamer queue control |
| Service/printer discovery and public aliases | PrintHub print-service catalog |
| Logical-to-physical submission tracking | PrintHub logical jobs plus print-service job IDs |
| Fleet Console | Studio printer/setup/job views; ZebraTamer standalone UI remains available |
| Fleet role/site/database features | Reduced service read/print/admin credentials; enterprise site/database features are intentionally out of scope |

## Baseline verification commands

Run these from the relevant repository before and after changes:

```text
cargo fmt --check
cargo test --locked
python -m pytest -q
npm test
docker compose config
docker compose up --build --detach --wait
```

Only commands supported by the component apply. Integration verification must
count jobs received by the virtual printer; HTTP success alone is insufficient.

## Known constraints

- No physical printer is available during the main implementation phase.
  Virtual TCP printers and deterministic renderer fixtures are the primary
  evidence until the hardware acceptance package can be executed.
- ZebraTamer currently accepts only `application/zpl` and has no TCP transport.
- Template printing currently chooses native ZPL; target-dependent raster
  output is not implemented.
- The existing IPP gateway models one configured PrintHub destination per
  process and needs a multi-queue lifecycle design.
- Published images and remote CI state are not inferred from local workflow
  files. AP-14/AP-19 require explicit release evidence.
