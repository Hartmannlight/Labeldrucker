# v1.0.0 hardware-qualification candidate 6

Status: qualification in progress; browser image output pending

This record fixes the artifacts used for the sixth stable hardware-
qualification candidate. It is not yet a hardware-acceptance record and does
not authorize a Compatibility Release. Any executable component source or
image change creates a different runtime candidate and requires the applicable
checks to be repeated. A newer workflow commit may add sanitized evidence,
release tooling or a qualification fixture without changing that runtime
identity, but every later fixture used for acceptance must be pinned below by
its own source revision and digest.

Candidate 6 replaces candidate 5 because Chrome landscape pages required a
tolerance-bounded orientation correction, the IPP queue did not expose an
operator-facing image policy, and Fleet promoted the Agent's initial `queued`
response too early.

## Deployed capability evidence

The persistent `printhub-qualification` volumes and unchanged Agent, Studio and
PostgreSQL services were retained. PrinterFleet, its worker, PrintHub, the IPP
gateway and the root-versioned Fleet Console run from the exact digests above.
All eight services run and every defined healthcheck is healthy.

The live CUPS IPP conformance probe passed without submitting a print job. It
reported exact borderless 50 x 25 mm media, monochrome output, 203 dpi, all four
standard orientations and `print-quality-supported= draft, normal, high`. The
existing Windows Microsoft IPP Class Driver queue still has an exact 50 x 25 mm
user ticket and zero queued jobs. Its refreshed PrintCapabilities expose
`Draft`, `Normal` and `High` output quality.

The mapping is:

- `Draft`: text/graphics threshold without dithering;
- `Normal`: automatic PrintHub content policy;
- `High`: photo policy with Floyd-Steinberg dithering.

Chrome may hide this standard option in its simplified dialog. The Windows
system dialog opened with `Ctrl+Shift+P` is the authoritative operator surface.
PrintHub also recognizes the observed approximately 25.025 x 50.049 mm Chrome
landscape page as the rotated form of 50 x 25 mm. Other media mismatches remain
held and require an explicit fit/fill decision.

## Stable transport scope

Candidate 6 can qualify only `print_agent` as an advertised stable transport
for `v1.0.0`. It exercises the exact pinned Agent image and a real Zebra over
USB. `raw_tcp` and `serial_over_tcp` remain usable beta capabilities, but they
must be recorded as `advertised: false` in the first stable hardware-acceptance
record because no representative physical Ethernet printer or serial bridge
was qualified. The virtual RAW-9100 printer proves integration and queue
isolation only; emulator success is not hardware acceptance.

This scope limits the compatibility promise rather than removing either
transport from PrinterFleet. A later compatibility release may advertise them
after their own real-device records pass the same independent review gate.

## Response-loss idempotency

The temporary `candidate6-virtual-zebra` route was enabled again for a
transport-independent response-loss test. A complete delivery request with
idempotency key `candidate-6-response-loss-20260906` was written directly to
PrinterFleet, but the client deliberately closed without reading the HTTP
response body. Fleet logs recorded the original request as `202 Accepted`, and
durable state contained exactly one delivery:

- Fleet delivery: `ce6d1cec-78bd-409c-bb9d-3156a3ea4093`
- artifact SHA-256:
  `5e8fa8766c424f0be42643cf7a0d2c496b25acd30f47d5c83c872ba441c830fd`
- attempts: 1
- terminal state: `transport_accepted`

Repeating the same request normally returned the existing delivery ID, and a
direct list query still found exactly one matching delivery. This proves the
Fleet API's durable response-loss idempotency: a caller that cannot observe an
accepted response can safely repeat the same logical submission without
creating a second delivery.

The emulator's volatile rendered-job list was no longer available after its
container restarted, so this test does not claim retained emulator evidence or
physical emission. At that point it did not replace the separate in-flight
disconnect scenario, which had to interrupt an active device transmission and
verify the honest `unconfirmed` outcome. The temporary printer was disabled
again after the test.

## In-flight Agent loss during USB transmission

The exact candidate PrintAgent was exercised against the attached
`zebra-lp2824-plus-usb` device without sending a printable format. The test
submitted 32 MiB of NUL bytes directly as `application/zpl`, with no ZPL command
or label terminator, under idempotency key
`candidate-6-inflight-crash-20260907`. Agent job
`2444c7fc-f15b-43d5-8a6c-fc6510afa0b9` durably entered `writing` on the real
`usb_bulk` path before the Agent process was terminated with `SIGKILL`.

The restarted Agent recovered that same job as:

- state: `outcome_unknown` (the Agent representation of an unconfirmed
  transmission);
- error: `agent_restarted_during_delivery`;
- bytes: 33,554,432;
- payload SHA-256:
  `83ee47245398adee79bd9c0a8bc57b821e92aba10f5f9ade8a5d1fae4d8c4302`.

Repeating the complete upload with the same payload and idempotency key returned
the original job ID and the unchanged `outcome_unknown` state. A direct list
query found exactly one matching job, no receiving/queued/writing/verifying
jobs and queue depth zero. The Agent then reopened the same USB printer, which
reported `present=true`, `open=true` and `ready=true`. No automatic resend took
place.

This deliberately non-printing payload proves persistence and ambiguity
handling on the actual USB write path without claiming a visible label result.
Fleet's mapping from Agent `outcome_unknown` to delivery `unconfirmed` and its
no-retry behavior remain covered by the pinned cross-component contract suite.
