## Recreated-stack baseline

The `printhub-qualification` project was removed with `docker compose down`
without deleting volumes and then recreated with the IPP, Studio, Fleet Console
and PrintAgent profiles from the digests above. Docker Desktop detached the
USBIP device when the former Agent container was removed. The operator workflow
therefore reattached only Zebra BUSID `1-8`, resolved its new dynamic device
node, applied the documented `root:zpl-agent` `0660` permissions, and recreated
the Agent with only that device node mapped.

After startup:

- all eight services were running and every defined healthcheck was healthy;
- the Fleet database retained exactly one printer and zero deliveries;
- Fleet worker's PostgreSQL healthcheck passed;
- Agent media remained 50 x 25 mm white direct-thermal gap media at 203 dpi;
- Agent configuration remained `LEFT POSITION +6`, `LABEL TOP +4`;
- the public PrintHub catalog exposed only `zebra-lp2824-usb` with the expected
  media and made it the default printer;
- the official CUPS `get-printer-attributes.test` passed and advertised exact
  50 x 25 mm borderless monochrome media at 203 dpi;
- the Agent process ran as UID/GID 999, `ippeveprinter` as UID/GID 10002,
  Avahi as UID 101 and D-Bus as UID 100 after guarded startup.

No print job was submitted during this baseline.

## Windows IPP ticket follow-up

Later Chrome attempts did not create PrintHub jobs. The Windows queue contained
two failed local spool jobs and PrintService event 372; the IPP gateway had only
received capability requests. A freshly recreated Microsoft IPP Class Driver
queue reproduced the cause: its global default rounded the advertised exact
50 x 25 mm medium to 2 x 1 inch (50.8 x 25.4 mm).

The project now includes `scripts/install_windows_ipp_printer.ps1`. It checks
the unrounded capability XML and validates the current Windows user's ticket as
exactly 50 x 25 mm. Both its repair mode and `-CheckOnly` succeeded locally;
the queue then reported no jobs and normal status. The Microsoft driver still
exposes its rounded global default, so every Windows user must run the repair
once in that user's account. A post-repair Chrome submission and its physical
result remain pending.

## Exact-image simulated queue isolation

A separate disposable PostgreSQL/Fleet environment used the candidate Fleet
and PostgreSQL digests. Two RAW-9100 emulators represented independent physical
queues. The fast endpoint listened immediately; the slow endpoint remained
unavailable for 12 seconds. Jobs were submitted in the order slow A1, fast B1,
slow A2.

- Fast B1 delivery `1c8d3f58-b379-454c-acd4-0e1d68cb9352` reached
  `transport_accepted` while slow A1 was still retrying.
- Slow A1 delivery `01bf48c4-a154-4d2d-a671-6f9183d340e6` had three bounded
  `retry_scheduled` transitions and was then accepted.
- Slow A2 delivery `c2fd0789-e6a6-4095-a4be-0650d59547cb` was accepted only
  after A1.
- The slow emulator observed exactly two connections in the order A1 then A2,
  with payload SHA-256 values
  `c46a7809e379e122a0e426db9f26139b6cc31a89260ae3a215ca0203371cda78`
  and
  `b689f5c1b73f22542537ec1e8d24501df3f24b9a382a5166ff80733cd3a58f3a`.
- The fast emulator observed exactly one B1 connection with payload SHA-256
  `460d85775c9d46cea05b3f1dbe318f3c88594ebfbb14b39dc3a9291b038f5997`.
- Repeating A1 with the same idempotency key returned the original delivery ID
  and caused no additional emulator connection.

This proves exact-image scheduler isolation, FIFO recovery and Fleet
idempotency. It does not replace the required counterpart with the physical
Zebra/PrintAgent path unavailable; that scenario remains pending.

## Media-state invalidation

With the Fleet delivery count at one, the authenticated Agent media API changed
the observed declaration from 50 x 25 mm to 50 x 24 mm. An explicit Agent
discovery refresh propagated 24 mm through Fleet to PrintHub. A uniquely
idempotent 50 x 25 mm raster job was then submitted with the safe `hold` policy.

- PrintHub job: `1f013716-a336-4fff-9664-bddf56d924da`
- Result: `held`
- Warning: `Document page is 50 x 25 mm but loaded media is 50 x 24 mm`
- Downstream Fleet delivery: none
- Fleet delivery count before and after: 1

The Agent declaration was restored in a guaranteed cleanup path. A second
discovery refresh and public PrintHub read both reported 50 x 25 mm again. This
proves stale preflight data is refreshed before release and a mismatch cannot
reach the device. The already running IPP service intentionally remains a
static advertisement until recreated; PrintHub is the live safety authority
for every received document.
