# Raspberry Pi 3A USB hardware acceptance — 2026-09-08

## Scope and result

This run validates the Fleet-free product path from a central PrintHub instance
to a real USB Zebra attached to a low-memory Raspberry Pi. It deliberately does
not exercise RAW TCP or port 9100.

Result: **accepted for the tested 64-bit Raspberry Pi / USB Zebra topology**.
The user physically confirmed that the standard 50 × 25 mm native test label
printed as intended. The raster path was accepted by the real USB transport and
accounted as a second label; transport acceptance remains distinct from a human
inspection of that second label.

## Hardware and software

- Edge host: Raspberry Pi 3 Model A, Debian 13 `trixie`, Linux `aarch64`
- Visible memory: 415 MiB RAM plus 414 MiB swap
- Root filesystem: 6.8 GiB total, 4.2 GiB available during the test
- Printer: Zebra ZTC LP 2824 Plus on `/dev/usb/lp0`
- USB identity: vendor/product `0a5f:00a3`
- Printer observations over the real reverse channel: firmware `V61.17.5Z`,
  hardware ID `V20.00.0`, 203 dpi, serial ending `3718`
- Agent: `zpl-agent 0.1.0`, SHA-256
  `4e07c5d836a4cdc49c35c38a4e8d3cb95b6a13af86c3a540d6959c615a419145`
- Deployment: native systemd unit, no Docker on the Pi

The enabled service ran as the dedicated `zpl-agent` user with supplementary
group `lp`, `TasksMax=32`, `MemoryMax=96M`, and 7 observed tasks. Resident memory
was about 6.0 MiB after the restart test. The host still reported 272 MiB RAM
available. The service token remained root-owned at mode `0640`; its transfer
staging copy was deleted after installation.

## Network note

The Windows host could reach the Pi directly, but containers in the local
Docker Desktop installation had no route to the Pi LAN address. For this test
only, an SSH local-forward bound on Windows loopback exposed the Pi agent to
PrintHub as `host.docker.internal`. This did not change the application protocol
or USB path, but it is not the intended permanent topology.

Before a Windows-hosted production rollout, allow Docker Desktop backend
traffic to the trusted LAN or use a Linux Docker host with direct routing. The
behavior and relevant host firewall boundary are described in Docker's
[networking documentation](https://docs.docker.com/desktop/features/networking/).
The product must not silently create an SSH tunnel and must not expose the
ZebraTamer API to an untrusted network.

## Reproduction outline

1. Verify the Pi is 64-bit and `/dev/usb/lp0` belongs to group `lp`.
2. Verify the downloaded ARM64 bundle checksum and review `config.toml`.
3. Run the native installer, then confirm `systemctl is-active zpl-agent` and
   `GET /healthz` locally and from the central host.
4. Register the service in Studio with its token, load the exact media, and
   confirm printer identity plus live ready state.
5. Send one native template job, replay its idempotency key, pause/cancel a
   queued job, and send one forced raster job.
6. Restart the service and verify identity, media accounting, job history and
   live status again.

No credentials, bearer tokens, passwords, or complete secret-bearing commands
belong in acceptance artifacts.
