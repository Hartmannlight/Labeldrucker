# Raspberry Pi standalone and onboarding plan

Status: active

## Approach

Turn the proven Raspberry Pi/GK420t installation into a supported product path
instead of documenting its manual workarounds. Keep protocol and policy in the
services that already own them: the host installer prepares Linux device and
DNS-SD integration, PrintAgent owns local hardware, PrinterFleet owns observed
printer/media state, PrintHub owns logical print policy, and the IPP gateway is
only a dynamically republished ingress.

## Scope

- In:
  - a pull-only ARM64/AMD64 SQLite standalone deployment;
  - idempotent Raspberry Pi host preparation for USB bulk and one DNS-SD
    advertisement;
  - USB discovery by stable hardware identity rather than bus/device number;
  - live media capability refresh, mismatch warnings and supported calibration
    or measurement actions;
  - a stable IPP queue name independent from the loaded roll;
  - a centrally enforced maximum labels-per-job policy with an authorized UI
    override;
  - guided setup verification and operator documentation.
- Out:
  - pretending that every printer can electronically measure its media;
  - inferring a physically correct print from successful USB transmission;
  - weakening the existing PostgreSQL enterprise profile or its immutable-
    digest validation;
  - exposing PrintAgent directly to workstation clients;
  - embedding host privilege escalation in a long-running container.

## Ownership and invariants

| Concern | Owner | Invariant |
| --- | --- | --- |
| Linux USB permissions and host DNS-SD | Pi host installer | Host mutations are explicit, reviewable and idempotent. |
| USB enumeration, reconnect and vendor commands | PrintAgent | Devices are selected by VID/PID/serial; a changing `/dev/bus/usb` path is not identity. |
| Desired and observed media state | PrinterFleet | Declared and measured values remain distinct and carry source, time and confidence. |
| Page count, copies and override authorization | PrintHub | Every ingress is subject to the same `pages × copies` limit before delivery. |
| IPP attributes and job-status translation | IPP gateway | It advertises only the authoritative current medium and never invents device state. |
| Guided setup and explicit confirmation | Fleet Console / Studio | UI warnings never bypass server-side authorization or policy. |

The public IPP printer name is stable (`PrintHub Label Printer` by default).
Media dimensions belong only in IPP media capabilities. A roll change therefore
does not create a second printer identity or a differently named queue.

For Raspberry Pi, exactly one component advertises the queue. The supported
default is a host Avahi service generated by the installer while container mDNS
is disabled. The IPP gateway binds its service independently from the hostname
placed into IPP/DNS-SD records, so a LAN address is never treated as a container
interface. Other deployments may deliberately select container-owned mDNS, but
the configuration validator rejects both announcers being enabled together.

Automatic media handling is capability based. A printer may report measured
width, length and tracking after calibration; unsupported values remain
`not_supported`, never guessed. PrinterFleet compares an observation with the
operator-declared roll using explicit tolerances. A mismatch blocks neither
status polling nor administration, but PrintHub continues to hold incompatible
jobs and the console shows a warning. Applying a measured size to the loaded-
media declaration is a separate, audited operator action.

## Validation

- A clean 64-bit Raspberry Pi OS host reaches healthy core, Studio and Fleet
  Console services using only released multi-architecture images and SQLite.
- After one explicit host-setup step, unplugging and reconnecting the GK420t
  changes its bus/device number but the Agent rediscovers the same identity and
  reports it ready without editing Compose.
- LAN discovery shows one reachable, stable printer name. IPP clients see only
  the currently declared label size after a roll change, without restarting the
  whole stack.
- A supported printer can calibrate and propose measured media; an unsupported
  printer clearly reports that manual dimensions are required.
- A job over the configured total-label limit creates no Fleet delivery. An
  authorized Studio user sees the computed total, confirms once, and the audit
  record identifies the override.
- Setup verification reports four independent facts: discovery, connectivity,
  media readiness and transport acceptance. Only the operator can mark the
  physical test label as visually correct.

## Implemented increments

- The pull-only SQLite profile, multi-architecture image lock and Pi host setup
  command cover steps 2 through 4.
- The IPP process is supervised and republishes capabilities when authoritative
  loaded media changes, while its stable display name and TLS directory remain
  unchanged. The Pi profile assigns DNS-SD exclusively to host Avahi.
- PrintHub holds `pages × copies` above the configured limit before Fleet
  delivery and exposes structured limit fields. Studio requires a separate
  confirmation to release such a job; IPP reports the hold without overriding
  it. Authentication and audit attribution for that override remain part of
  step 8, so the step is deliberately not marked complete.
- PrinterFleet exposes a partial measured height only when a Zebra device
  configuration returns an unambiguous label length. Missing readback remains
  `unknown`, width remains unset, and Fleet Console warns on a measured-height
  mismatch instead of claiming unsupported automatic detection.

## Open questions and working defaults

- Default maximum: 25 labels per logical job. Operators may change it through
  deployment configuration; no ingress gets a separate higher limit.
- Initial Pi support: 64-bit Raspberry Pi OS / Debian with systemd, udev and
  Avahi. Other Linux distributions keep the generic Compose path.
- Media tolerance: start with the existing PrintHub physical-size tolerance;
  vendor observations also include confidence so future hardware can provide a
  more precise threshold without changing the generic contract.
- The first setup command is CLI-driven and noninteractive-capable. The browser
  wizard consumes the same APIs later rather than becoming a second installer.
